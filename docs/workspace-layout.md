# 工作区格式

用户选中的任意可写文件夹就是一个项目。应用直接索引其中的图片，不复制图片，也不接管用户原有的多级目录分类。

```text
MyDataset/
├─ group-a/
│  ├─ image-001.webp
│  ├─ image-001.txt          # 可选：迁移前已有的旧标注
│  └─ image-001.json         # 可选：Prompt 元数据
├─ group-b/
│  └─ image-002.png
└─ .annotation-workspace/
   ├─ project.json
   ├─ state.sqlite3
   ├─ thumbnails/
   ├─ history/
   ├─ validation/
   ├─ runs/
   ├─ recovery/
   ├─ cache/
   └─ logs/
```

## 标注的真实来源

`state.sqlite3` 是标注的唯一活动来源。Tagger、LLM、人工编辑和翻译都只创建数据库修订，运行过程中不再写图片旁的
TXT。图片旁的旧文件有以下边界：

- 首次升级到数据库标注存储时，同名 `.txt` 导入“原有标注”通道；`图片名.语言代码.txt` 导入对应翻译通道。
- 导入内容被记录为迁移时确实存在，但应用不猜测它是 Tags、描述还是其它自定义文本。
- 迁移前先把项目 SQLite 备份到 `history/pre-annotation-store-v2-*.sqlite3`。
- 导入成功后旧文件原样保留，不自动删除；之后在外部修改它不会反向覆盖数据库。
- 同名 `.json` 仍是只读 Prompt 元数据，不属于标注存储。

因此，数据库迁移完成后的 TXT 只可能是旧输入或用户明确导出的产物，不是旁路写入接口。

## 标注通道、可用性与人工复核

每张图片可以同时拥有多个独立通道：

| 通道 | 内容 | 典型写入方 |
| --- | --- | --- |
| 原有标注 `existing_annotation` | 不推断语义的纯文本 | 旧 TXT 导入、人工修订 |
| Tags `tags` | 有顺序的结构化 Tag；可带类别、置信度和来源 | 本地 Tagger、人工增删 |
| LLM 描述 `description` | 模型原始文本 | 多模态模型、人工修订 |
| 翻译 `translation:<language>` | 每种语言独立的纯文本 | 翻译任务、人工修订 |

每个通道保存不可变修订，并分别维护：

- `head_revision_id`：编辑器当前看到的版本；
- `reviewed_revision_id`：用户最近一次明确人工复核的版本，仅作为质量管理标记；
- 生成时对应的图片内容哈希；
- 来源任务、输入修订和生成参数元数据。

当前 head 只要校验通过、不是墓碑且绑定当前图片，就处于“当前可用”状态；译文还必须继续依赖当前优先源标注
的 revision。满足这些条件后无需先人工复核即可参与翻译、Tag 辅助、统计和默认导出。人工复核与可用性相互
独立：复核不会替代校验，也不会把无效内容变成有效内容。
Tagger、LLM、翻译结果和新导入的旧 TXT 默认尚未复核，但通过校验后立即可用。

图片内容或译文源修订变化后，原修订显示为“已过期”。用户可以在单图编辑器复核，也可以在素材列表打开批量操作页，按
Tags、LLM 描述、原有标注或具体译文语言选择要复核的类别；对过期版本执行复核会为当前图片创建新修订，而不是
改写旧历史；过期译文会同时绑定当前源 revision。校验失败或缺少当前源的内容会明确列为不可复核，不会中断其它
目标。批量删除使用同一套数据库范围预览，只列出所选图片中实际存在的类别，并只为勾选通道写入墓碑修订，
历史内容仍可查看和恢复到编辑器。“原有标注”页签默认隐藏，仅在当前素材确实存在导入内容时显示。

### 批量编辑 Tags

素材列表的“已选 N 张”范围可以打开“批量编辑 Tags”，执行添加、替换或删除。操作仍然为每张实际变化的
图片创建独立、不可变的 Tags 修订，不会生成额外的批次记录，也不提供跨图片的一键撤销。每张图片仍可从
自己的 Tags 历史恢复旧版本。

- Tag 名称按去除首尾空白后的大小写不敏感精确值匹配，不做子串替换；请求内重复项保留首次出现顺序。
- 添加默认在原列表末尾按输入顺序追加，也可以选择列表开头、第 N 位，或指定 Tag 的前后位置；已存在项保持原位并跳过。
  第 N 位按每张图片自己的列表解释，越过当前长度时夹到末尾；锚点按大小写不敏感的精确名称匹配，找不到锚点的图片会跳过。
  新增项始终作为连续块插入，并保留输入顺序；没有 Tags 通道或当前为删除修订时，开头、末尾和序号位置会创建或恢复通道。
- 删除只移除命中项并保留其余顺序。删掉最后一个 Tag 时写入活动的 `empty` 修订，不写通道墓碑。
- 替换只处理包含旧 Tag 的图片。目标不存在时写入旧位置；目标已经存在时移除旧项并保留原目标位置，避免重复。
- 新增或替换项的类别来自所选词库建议或为空，`confidence` 为空，`origin` 为 `manual`。新 head 默认尚未复核，
  并绑定执行时的当前图片哈希；过期 Tags 因此可以在实际变化时重新绑定当前图片。

预览接口会返回修改/跳过数量、通道创建或恢复数量、空结果、过期重绑定、逐 Tag 增删数量、定位跳过和序号夹到末尾数量，以及当前依赖
Tags head 且将变为不匹配的译文数量。执行必须重复同一规范化请求并携带预览令牌；令牌覆盖素材、图片哈希、
Tags head 和变换结果。服务会先持有所选图片的全部 Tags 输出租约，再重建并校验计划，最后用一个 SQLite
事务写入所有新修订。令牌过期、租约冲突、素材变化或任一写入失败都不会留下部分结果。

预览还会按素材相对路径分页展示每张图片的“修改前 / 修改后”完整 Tags 顺序，并标出实际新增和删除的位置。
这里直接使用底层 Tags 数组，不按单图编辑器的类别分组重新排列，因此序号就是执行后保存的真实位置。默认只列出
实际变化的图片，也可以查看锚点定位跳过或全部所选图片；切换预览范围和页码不会改变批量操作及其预览令牌。

Tags head 变化后，依赖旧修订的 Tags 来源译文自然显示为不匹配，需要重新生成。任务创建时已经冻结的
Tags 输入 revision 不会被批量编辑改写，排队任务仍按原快照执行。

## Tagger 辅助 LLM

Tagger 始终写入独立的 Tags 通道。“使用 Tags 辅助 LLM”是素材页“提示词”区域中的项目设置，
与 System Prompt 和 User Prompt 一起保存：

1. 任务创建事务逐图冻结当时通过校验且匹配当前图片的 Tags `head_revision_id`；
2. Worker 读取该固定修订的 Tag 名称；
3. 在 JSON 元数据行之后追加 `tags: ["tag_a","tag_b"]` 到 User Prompt；
4. LLM 结果写入独立的 LLM 描述通道。

开关默认关闭。素材页会分别展示 Tags 追加状态、准确的追加行以及最终 User Prompt；没有可用 Tags 的图片仍正常执行，
只是不追加辅助行。任务创建后继续编辑或复核 Tags，不会改变该任务已经冻结的输入。

## 内部目录

- `project.json`：稳定项目 ID、名称和项目级 Prompt / 扫描设置。
- `state.sqlite3`：图片索引、标注文档与修订、结构化 Tags、修订依赖、任务、请求尝试、导出与预处理记录。
- `runs/`：远端请求或本地 Tagger 推理的脱敏成功/失败产物；不保存图片副本。
- `history/`：迁移前数据库备份等长期历史文件。
- `recovery/`：预处理前的原文件，以及可撤销的素材文件包。
- `thumbnails/`、`cache/`、`validation/`：可重建派生数据。

整个目录移动后，`project.json` 中的稳定 ID 不变。再次选择新路径时，全局“最近项目”记录会更新到新位置。最近路径身份遵循当前操作系统：Windows 忽略大小写，Linux 保留大小写。

## 导出目录

导出目录不属于项目内部结构。用户选择一个已经存在的文件夹；文件夹输出要求目录为空，ZIP 输出允许目录包含
其他内容，但同名目标归档必须不存在。每个“通道 + 语言”可以独立选择当前或已复核 revision，同一请求也可以
选择多个译文语言。预览会冻结图片哈希、所选通道的具体 revision ID 以及最终内容，Worker 只物化该快照。

单通道 TXT 仍提供常见的扁平训练集：

```text
Export/
├─ image-001.webp
└─ image-001.txt
```

同时选择多个 TXT 通道时，每个通道成为独立训练集变体，避免把不同语义强行合并：

```text
Export/
├─ tags/
│  ├─ image-001.webp
│  └─ image-001.txt
├─ description/
│  ├─ image-001.webp
│  └─ image-001.txt
└─ translation-zh-CN/
   ├─ image-001.webp
   └─ image-001.txt
```

JSON 可以单独选择，也可以与 TXT 同时选择。逐图 `*.annotations.json` 会保留所有所选通道、修订 ID、可用状态、
人工复核状态、校验状态和结构化 Tag 字段；多通道 TXT 同时启用时，JSON 放在 `metadata/`。

目录结构可以选择：

- `flat`：兼容旧行为，移除素材的工作区父目录；
- `preserve`：保留工作区根目录名，并保留素材相对于工作区根目录的当前目录；
- `custom`：以工作区根目录名为外层目录，从保留结构开始，把明确选择的目录内容并入其父级。规则匹配原始工作区
  相对路径，选择父目录不会隐式选择其后代；同时选择父目录和子目录时会累计移除两个层级。

自定义规则树与当前导出范围保持一致：“候选工作集”只统计当前有效候选集（候选集为空时才回退到整个项目），
“工作台选中”只统计当前勾选且仍存在的图片。切换范围或改变工作台选择后，不再存在于新范围中的规则会被移除。

例如工作区名为 `MyDataset` 时，`characters/alice/set-1/image.webp` 在保留模式下会输出到
`MyDataset/characters/alice/set-1/image.webp`；自定义选择 `characters/alice` 后变为
`MyDataset/set-1/image.webp`。多通道 TXT 会把这一结构放在 `tags/`、`description/` 等通道目录之下，
ZIP 内部使用完全相同的目标路径。

输出方式可以选择文件夹或 ZIP。ZIP 模式在所选目录中生成一个与目录同名的 `.zip` 文件，归档内目录结构与
文件夹模式一致。目录中的其他内容保持不变；同名归档存在时预览会阻止任务。Worker 以固定大小的数据块直接写入
临时归档，不把整套数据载入内存；完成后原子发布最终文件。停止或意外中断会删除临时归档，继续任务时从头
重新打包。

默认导出当前 head；用户也可以逐通道显式限制为已人工复核版本。尚未复核本身不产生导出警告，图片变化、
译文源变化、缺失或
校验异常仍会在预览中提示。文件夹模式目标目录非空、ZIP 模式同名归档已存在、图片变化、路径越界和最终目标
名称冲突、大小写冲突以及目标文件与目录的前缀冲突属于不可绕过错误。继续已停止任务前会校验已经写出的文件，
绝不覆盖用户后来修改的内容。

## 数据安全约束

标注修订是 SQLite 事务，不与 TXT 双写。输出资源租约以“素材 ID + 通道 + 语言”为键，防止编辑器、Tagger、LLM
或翻译任务同时覆盖同一通道；不同通道可以独立工作。任务只释放自己认领的条目租约，前台租约还携带进程角色
和实例标识，恢复逻辑不会清空其它仍在执行的操作。

预处理和素材删除仍可能处理图片旁的旧 TXT、旧译文和同名 JSON，因为这些文件是用户数据集中的普通伴随文件。此类文件操作继续遵循
“预览计划 → 私有 staging / recovery → 顺序提交 → 失败补偿”，但不会把外部 TXT 重新认定为活动标注。
